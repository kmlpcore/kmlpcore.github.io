Overview

One reliable journey from registration to receipt, where a registration exists only when its payment is verified.

AEMS is a web platform built for Abhinayaa Institute of Research & Fine Arts to streamline examination registration and fee payment. It joins student registration, examination selection, document submission, payment, verification, and receipt generation into one flow. V1 set up the digital registration workflow. V2 added an integrated payment flow, stronger transaction handling, document validation, duplicate-payment protection, and automated receipts.

What the system had to do

  • Collect student and examination details online
  • Match the chosen examination to the correct fee
  • Accept the required examination documents
  • Process fee payments online
  • Verify payment before finalising a registration
  • Prevent duplicate registrations for one payment
  • Store records in a structured database
  • Generate a formal digital receipt

The problem

Examination registration had to bring together student details, the chosen examination, supporting documents, fee collection, and registration records. It was bigger than an online form: the system had to connect every stage of a real transaction, and create a registration only when its payment was truly verified.

The core questionHow can examination registration become one reliable digital workflow instead of a collection of disconnected steps?

V2 grew out of the first version as operational needs changed. It was not an unrelated replacement.

The V2 journey

One principle drove the design: no final registration until the payment is verified.

  1. 1Student registrationThe student enters personal and examination details.
  2. 2Fee determinationThe server decides the expected fee for the chosen examination.
  3. 3PaymentThe student pays through Cashfree.
  4. 4Payment verificationThe backend checks the payment against the expected order and amount.
  5. 5Document validationThe submitted document is checked before final storage.
  6. 6Registration creationThe verified transaction and student data are saved as the final registration.
  7. 7Digital receiptA formal receipt is generated with registration and payment details.

Under the hood

The three places where a real transaction can go wrong, and how V2 handles each.

Payment verification

V2 moved from showing payment information to verifying a real transaction. The backend retrieves the payment from Cashfree and checks:

  • Payment status
  • Payment amount
  • Order amount
  • Currency
  • Accepted payment method
  • Cashfree payment ID

Duplicate protection

Retries and repeated requests can create duplicate records. Before creating a registration, V2 checks whether the payment ID already exists in the registrations table.

If it does, the system returns the existing registration instead of creating another.

Document validation

File handling is part of the application logic, not just an upload field.

  • The upload is present and successful
  • File size is checked
  • The real MIME type is inspected
  • Only PDF, JPG, and PNG are accepted
  • A controlled filename is generated
  • Moved to final storage only after payment verification

The workflow also plans for failure. If a verified payment cannot be saved as a registration, the newly stored document is removed and an error is returned, instead of showing a false success.

Engineering decisions

Server-side fee validation

The backend decides the expected fee, not just the values sent from the frontend.

Payment-first registration

A registration exists only after a successful payment is verified.

Payment-ID deduplication

A repeated request returns the existing registration instead of creating a duplicate.

Validated uploads

File presence, size, and real MIME type are checked before storage.

Controlled storage

Files are renamed with generated tokens, not the original filename.

Failure-aware processing

No apparently successful but incomplete record is left behind.

Connecting payment and registration

A payment click on the frontend cannot mark a registration successful, so V2 verifies on the server first.

Keeping data consistent

Payment verification, document storage, and the database insert depend on each other, so they run in a strict order.

Evolving a live system

I had to understand what V1 already did before changing it, and connect the new parts without breaking registrations that already worked.

Outcome

AEMS grew from a basic online registration portal into a connected transaction workflow. 30+ students registered in the first week, and for the annual examinations on this November the registrations have touched 140+ registrations (including other branches and affiliation centers). The portal is updated for each upcoming examination.

The resultStudent data + documents + payments + registration + receipt = one connected workflow.

What I learned

A form can collect information, but a reliable production workflow has to account for validation, failed transactions, duplicate requests, file handling, database consistency, and user experience. Moving from V1 to V2 also showed me how real software evolves around changing requirements.

Built for a real organisation, so no credentials, student documents, or personal data are shown here. The source code is in a private repository, and a sanitised version can be shared for interview evaluation.
